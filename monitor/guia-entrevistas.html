2Base de datos: las consultas del día

Todas estas corrieron HOY contra la base real. Estúdialas en este orden: cada una introduce una idea nueva.

2.1 · SELECT: leer con filtro, orden y límite

SELECT id, creado_en, etapa, LEFT(entrada,120)
FROM mensajes
WHERE wa_id = '573167404278'
ORDER BY id;
  • WHERE filtra filas; ORDER BY las ordena; LIMIT n corta el resultado.
  • LEFT(col, 120) recorta el texto a 120 caracteres — para no inundar la pantalla.
  • \G al final (en el cliente MySQL) muestra cada fila en vertical: útil con columnas largas.
Caso real: con esta consulta reconstruimos la conversación de Maryluz y descubrimos que el bot le mandó "Cerramos esta conversación" tres veces.

2.2 · UPDATE con CONCAT: agregar sin borrar

UPDATE leads
SET detalle = CONCAT(detalle, '\n➕ El material es para 5 puertas de 2,10 x 0.80')
WHERE id = 332 AND LOCATE('5 puertas', detalle) = 0;
  • CONCAT(a, b) pega textos. Aquí sumamos al detalle en vez de reemplazarlo.
  • LOCATE(aguja, pajar) = 0 significa "el texto NO está todavía" → la consulta es idempotente: córrela dos veces y no duplica. Esa palabra vale oro en entrevistas.

2.3 · El candado NOT EXISTS: ganarle a una carrera desde SQL

INSERT INTO leads (...)
SELECT ...
WHERE NOT EXISTS (
  SELECT 1 FROM leads
  WHERE telefono = ? AND creado_en > NOW() - INTERVAL 45 MINUTE
);

Dos mensajes del mismo cliente pueden llegar con 22 ms de diferencia y ejecutarse en paralelo. El código JavaScript no alcanza a enterarse — pero la base de datos serializa las escrituras: el segundo INSERT ve al primero y no inserta. La BD es la última línea de defensa contra duplicados.

2.4 · Comparar teléfonos como TEXTO (la trampa del tipo de dato)

-- MAL: revienta si en la tabla hay un id no numérico como 'CO.1352055013679988'
WHERE telefono = 573125758845
-- BIEN: se compara texto con texto, con la intercalación correcta
WHERE telefono = CONVERT('573125758845' USING utf8mb4) COLLATE utf8mb4_unicode_ci
Caso real: el lead de una clienta se perdió con el "quedó registrada" ya enviado, porque comparar contra un número hacía abortar el INSERT cuando la tabla tenía un usuario con número oculto (BSUID). Un tipo de dato mal comparado = un cliente perdido.

2.5 · GROUP_CONCAT: una lista en una sola celda

SELECT GROUP_CONCAT(DISTINCT wa_id SEPARATOR ',')
FROM mensajes
WHERE etapa = 'cierre_inactividad'
  AND creado_en > NOW() - INTERVAL 3 HOUR;

Devuelve 573167…,573205… — todos los clientes que ya recibieron el cierre, en una sola fila. Hoy la usamos para que el cron le pregunte a la BD "¿a quién ya le mandé esto?" antes de repetir un mensaje.

2.6 · Marcadores vs. interpolar (inyección SQL)

-- NUNCA: pegar el valor dentro del texto de la consulta
"UPDATE config SET valor='" + token + "'"
-- SIEMPRE: marcadores; el driver escapa por ti ($1 en n8n, ? en otros)
UPDATE leads SET detalle = CONCAT(detalle, '➕ ', $1) WHERE telefono = $2

Interpolar abre la puerta a la inyección SQL (el clásico de entrevista: '; DROP TABLE--) y a errores de tipo silenciosos. En n8n los marcadores son $1, $2 — con ? da error de sintaxis que falla en silencio.

2.7 · DELETE con guardas: borrar es para siempre

DELETE FROM leads
WHERE id = 341 AND modo_prueba = 1;

Nota las dos condiciones: el id exacto Y que sea un registro de prueba. Si el id estuviera mal, la segunda condición salva. Regla de la casa: todo DELETE lleva una condición extra que lo haga inofensivo si te equivocas — y el usuario de la aplicación (n8nbot) ni siquiera tiene permiso de DELETE. Eso se llama mínimo privilegio.

4Endpoints y métodos HTTP

"¿Cómo se hace un endpoint?" — la respuesta corta: un endpoint es una URL que acepta un MÉTODO y cumple un CONTRATO (qué recibe, qué responde). Nuestro sistema tiene endpoints de los dos lados: los que exponemos y los que consumimos.

4.1 · Los métodos, con nuestros ejemplos reales

MétodoSemánticaEjemplo real de hoy
GETLeer, sin efectosGET /api/v1/workflows/botArdisaFase1x — bajar el workflow vivo para el diff
POSTCrear / disparar una acciónMeta hace POST /webhook/bot-wsp-ardisa-f1 con cada mensaje; nosotros hacemos POST a Meta para responder
PUTReemplazar el recurso completoPUT /api/v1/workflows/… — el deploy "en caliente" que estrenamos hoy
DELETEEliminarDELETE /api/v1/workflows/{id} — borrar el workflow desechable de la prueba

4.2 · Cómo se crea un endpoint (nuestro webhook)

En n8n, el nodo Webhook declara: método POST, ruta /webhook/bot-wsp-ardisa-f1. Con eso n8n "registra la ruta": cuando llega un POST ahí, arranca el workflow. En cualquier framework es la misma idea:

// La idea universal (aquí en Express/JavaScript):
app.post('/webhook/bot', (req, res) => {
  const firma = req.headers['x-hub-signature-256'];  // 1. autenticar
  if (!verificar(firma, req.rawBody)) return res.status(403).end();
  procesar(req.body);                                  // 2. actuar
  res.status(200).json({ ok: true });                  // 3. responder RÁPIDO
});

Detalle de producción: a Meta hay que responderle 200 rápido (aunque el trabajo siga por detrás), o reintenta y te duplica mensajes. Y la firma HMAC-SHA256 del header demuestra que el POST viene de Meta y no de un extraño: se calcula sobre el cuerpo crudo con un secreto compartido y se compara con comparación de tiempo constante.

4.4 · Anatomía de un curl (la navaja del día)

curl -s -m 10 \
  -X POST https://mcp.ardisa.com/mcp \
  -H 'Content-Type: application/json' \
  -H "Authorization: Bearer $TOKEN" \
  -d '{"jsonrpc":"2.0","method":"initialize", ...}' \
  -w "http=%{http_code}\n" -o /dev/null
  • -X el método · -H un header · -d el cuerpo · -s silencioso · -m 10 máximo 10 segundos.
  • -w "%{http_code}" imprime el código de estado · -o /dev/null descarta el cuerpo.
  • Con esto probamos hoy: el webhook, la API de n8n, el MCP, la tienda Magento y el flujo OAuth. curl es tu laboratorio de endpoints.

5OAuth: la historia del token caído

Hoy viviste el ciclo de vida COMPLETO de OAuth en producción, con falla incluida. Cuéntalo así y cualquier entrevistador te para bolas.

  1. Registro del cliente — POST /register: la aplicación se presenta y recibe client_id + client_secret.
  2. Autorización — el navegador va a /authorize; la persona (tú) inicia sesión y da permiso ("Allow Access"). Vuelve un código de un solo uso.
  3. Intercambio — POST /token con el código → devuelve access_token (corto, ~1 hora) + refresh_token (largo).
  4. Uso — cada llamada lleva Authorization: Bearer <access_token>.
  5. Renovación — antes de vencer, POST /token con grant_type=refresh_token. Nuestro cron lo hace cada 10 minutos.
La falla de hoy (y la lección): el servidor MCP se reinició y olvidó los clientes registrados. El token "se veía" vigente (le quedaban 49 min según el reloj local) pero el servidor lo rechazaba con 401. Lección: la validez de una credencial la decide quien la recibe, no quien la tiene. El refrescador ahora le pregunta AL SERVIDOR (una llamada de sondeo) en vez de confiar en su reloj. Y la recuperación fue: borrar las credenciales muertas → re-registrar el cliente → repetir la autorización.
Frase de entrevista

"Depuré un 401 en producción hasta la causa raíz: el servidor OAuth perdió el registro del cliente tras un reinicio. Dejé un monitoreo que valida el token contra el servidor — no contra el reloj local — y documenté la recuperación."

6Conceptos de ingeniería (con su cicatriz)

Cada concepto de esta lista tiene un caso real de HOY. En entrevista, el concepto + la historia vale por diez definiciones de memoria.

Condición de carrera (race condition)

Dos procesos leen el mismo estado "viejo" y escriben encima el uno del otro — gana el último (last-write-wins). Hoy: una cotización de 4½ minutos guardó la memoria vieja del bot y "resucitó" a una clienta ya despedida; el cron la volvió a despedir dos veces. Arreglo: la verdad se consulta en la BD, que serializa.

Idempotencia

Una operación que puedes repetir sin cambiar el resultado. Hoy: el UPDATE con LOCATE(...)=0, y el candado del cron que pregunta "¿ya le mandé el cierre?" antes de mandarlo. Los sistemas distribuidos REPITEN cosas (Meta reintenta webhooks); tu código debe aguantar la repetición.

Timeout vs. tope de reloj

Un timeout de socket corta conexiones muertas. Pero un stream que manda "pings" se mantiene técnicamente vivo… sin decir nada útil. Hoy: llamadas al MCP colgadas 284 segundos con timeout de 45 configurado. Arreglo: Promise.race entre la llamada y un reloj propio — pase lo que pase en el socket, a los 30 s seguimos.

Serie vs. paralelo

Seis consultas en serie suman sus esperas; en paralelo, esperas solo la más lenta. Hoy: el nodo de consultas SAP pasó de 6 llamadas en fila (64 s si una se colgaba) a Promise.all con deduplicación. La espera del cliente bajó de 4½ minutos a ~1.

Reintentos con criterio

Reintentar sirve para fallas transitorias (red, un 500 suelto). Reintentar un cuelgue de 30 segundos = regalar otros 30. Hoy: reintentamos solo fallas rápidas; el silencio largo no se repite.

Degradación elegante

Cuando una pieza falla, el sistema entrega lo que sí puede en vez de romperse. Hoy: con SAP mudo, el bot igual dio el precio que sí llegó y cerró el lead con la asesora — el cliente nunca vio un error.

Watchdog (perro guardián)

Un proceso aparte que vigila al sistema y grita cuando algo se sale de lo normal. Hoy: el vigilante detectó por sí solo a la clienta no registrada, y le añadimos la regla "ejecución corriendo >10 minutos = alerta". El complemento del watchdog es el techo duro: executionTimeout: 300 — probado en vivo, cortó a los 300.0 segundos exactos.

Deploy sin caída (hot deploy)

Actualizar el sistema sin apagarlo. Hoy: descubrimos que el ciclo apagar→subir→prender dejaba el webhook muerto 4 segundos (ahí se perdió un mensaje real); probamos en un workflow desechable que n8n acepta PUT en caliente, y el deploy quedó sin ventana de pérdida. Método: nunca pruebes un cambio de deploy en el sistema vivo — móntate un desechable.

Fuente única de verdad

Todo el bot se genera desde build_f1.py: el workflow, los nodos, el SQL. Nadie edita "a mano" lo desplegado; el build valida sintaxis y las pruebas corren antes de cada deploy. Si lo vivo difiere del build, el deploy aborta.

Cada bug deja una prueba

Hoy nacieron test_adicion_queda_en_bd.js (10 aserciones), test_cierre_no_se_repite.js (5) y creció test_mcp_en_casa.js — cada una reproduce el bug del día con los datos reales (hasta los espacios raros del catálogo). Un bug con prueba no vuelve; un bug sin prueba es una promesa.

9Construye tu primera API (clase práctica)

El ejercicio clásico de entrevista junior: un CRUD REST. Lo construiste el 20 de agosto en ~/practica-api. Repásalo hasta poder escribirlo de memoria.

La receta completa

mkdir -p ~/practica-api && cd ~/practica-api
npm init -y && npm install express
const express = require('express');
const app = express();
app.use(express.json());  // sin esto, req.body llega vacio en los POST

let productos = [
  { id: 1, nombre: 'Varilla de hierro 12mm', precio: 28551 },
  { id: 2, nombre: 'MDF 183x244x2.7 crudo',  precio: 39439 },
];

// LEER la lista
app.get('/productos', (req, res) => res.json(productos));

// LEER uno — ":id" es parametro de RUTA
app.get('/productos/:id', (req, res) => {
  const p = productos.find(x => x.id === Number(req.params.id));
  if (!p) return res.status(404).json({ error: 'no existe' });
  res.json(p);
});

// CREAR — los datos vienen en el CUERPO (req.body); valida y responde 201
app.post('/productos', (req, res) => {
  if (!req.body.nombre) return res.status(400).json({ error: 'falta el nombre' });
  const nuevo = { id: productos.length + 1, nombre: req.body.nombre, precio: req.body.precio || 0 };
  productos.push(nuevo);
  res.status(201).json(nuevo);
});

// REEMPLAZAR uno
app.put('/productos/:id', (req, res) => {
  const i = productos.findIndex(x => x.id === Number(req.params.id));
  if (i < 0) return res.status(404).json({ error: 'no existe' });
  productos[i] = { id: Number(req.params.id), nombre: req.body.nombre, precio: req.body.precio };
  res.json(productos[i]);
});

// BORRAR — 204 = hecho, sin contenido
app.delete('/productos/:id', (req, res) => {
  productos = productos.filter(x => x.id !== Number(req.params.id));
  res.status(204).end();
});

app.listen(3000, () => console.log('API viva en http://localhost:3000'));

Pruebala con curl (tu propio cliente)

curl -s localhost:3000/productos
curl -s localhost:3000/productos/2
curl -s -X POST localhost:3000/productos -H 'Content-Type: application/json' \
     -d '{"nombre":"Tapacanto blanco","precio":1200}'
curl -s -X PUT localhost:3000/productos/1 -H 'Content-Type: application/json' \
     -d '{"nombre":"Varilla 12mm x 6m","precio":29000}'
curl -s -w "http=%{http_code}\n" -X DELETE localhost:3000/productos/2
  • Ruta vs. cuerpo: el quien va en la ruta (/productos/2); el que va en el cuerpo JSON.
  • Codigos con intencion: 200 leer, 201 crear, 204 borrar, 400 datos malos, 404 no existe.
  • El puente con el bot: el webhook de Meta es un app.post('/webhook/...') igual a tu app.post('/productos') — recibe JSON, valida (alla la firma HMAC), actua y responde un codigo.
